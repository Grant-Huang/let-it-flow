# 加拿大橱柜报价平台 —— 需求说明书（v0.2）

> 本版整合了与 Grant 多轮讨论后确认的决策。v0.1（对话讨论稿）里的 7 个待确认问题已全部关闭，
> 新增的开放问题见第 11 节。本文档仍处于"确认阶段"——确认后再转入开发任务拆解，当前分支上
> 已有的 `leads.ts`/`email.ts`/`server.ts`/`web/index.html` 是上一版范围（批量搜索+群发询价信）
> 的实现，与本版需求的关系见第 10 节，尚未按本版需求改动代码。

---

## 1. 业务背景与目标

客户要装修厨房，需要跟多家橱柜公司比价。人工做法是：分别联系每家公司 → 描述户型和需求 →
等对方出图纸和报价 → 反复修改。本系统的目标：客户在**一个对话界面**里完成"设计沟通 → 平面图
确认 → 报价单确认 → 发送给对应公司"的全流程，且设计建议**严格遵守每家公司自己的产品规格**。

---

## 2. 角色与参与方

| 角色 | 说明 |
|---|---|
| **客户（Customer）** | 终端用户，在对话框里描述需求、上传户型图、确认设计与报价 |
| **总控助手（Orchestrator）** | 对话框默认对话对象，负责通用橱柜设计知识、理解户型和需求、把问题路由给具体公司 Agent |
| **橱柜公司 Agent（Company Agent）** | 每家已入驻公司一个，绑定该公司的产品规格库，只回答/只设计"自己公司能做到的" |
| **橱柜公司（Company）** | 现实中的橱柜厂商/经销商，最终报价邮件的接收方 |
| **公司运营/店长** | 使用"公司入驻规格录入会话"整理自家产品规格的人 |

## 3. 核心概念

### 3.1 多 Agent 对话架构
- 客户默认与总控助手对话（通用设计知识：风格/预算/大致想法）。
- 客户可用 `@公司名` 把具体问题路由给该公司 Agent（如"@枫叶橱柜 你们有 36 寸转角柜吗"），
  同一句话可以 @ 多家公司做横向提问。
- 公司 Agent 的回答**必须基于该公司规格库**，不得编造/借用其他公司信息。

### 3.2 公司产品规格库（Product Spec）
每家公司的规格库至少包含：
- 柜体类型（地柜/吊柜/高柜/转角柜等）及每种类型的标准尺寸候选集（宽×高×深，离散值）
- 每个具体型号所属的**"脸型模板"**（见 3.3）——决定它在正视图上怎么画
- 门板花色/材质选项、五金选项、定价规则

### 3.3 渲染架构：脸型模板库 + 参数化拼接（本版新增，替换 v0.1 的笼统方案）

**结论先行：不让 LLM 直接生成图形坐标，也不引入 CAD 引擎或第三方素材库（如 Sweet Home 3D——
其素材本质是 3D 模型的俯视投影，且是通用款式，无法对应具体公司的真实型号，弃用）。**

正确的分工是"代码算布局数字，代码画图"，且利用 RTA（现货组装）橱柜品类本身高度标准化的特点，
把渲染进一步简化成**小模板库 + 参数化拼接**：

1. **布局计算**（确定性算法，非 AI）：给定墙面可用长度（户型图解析得出）+ 该公司规格库里的
   离散尺寸候选集，做贴墙排布（类似一维装箱/cut-list optimization），算出每个型号的精确
   位置（x/y/宽/高/深，单位英寸，精度到 1/4 英寸）。
2. **脸型模板库**（一次性手绘/手写的 SVG symbol，数量级如下，覆盖绝大多数 RTA 配置）：

   | 视图 | 模板数量级 | 举例 |
   |---|---|---|
   | 正视图 Front | ~10-15 个 | 单门柜、双门柜、三抽屉、一门一抽、转角盲柜、水槽柜、单门/双门吊柜、开放格 |
   | 俯视图 Top（地柜层/顶柜层分开出图）| ~3-5 个 | 外框矩形、转角柜斜切角、开门弧线示意 |
   | 侧视图 Side | ~2-4 个 | 地柜截面、吊柜截面（同一趟柜子复用同一模板，标准台面高度/净空按行业惯例标注）|

3. **渲染**：用 SVG 原生 `<symbol>` + `<use>` 机制，对每个已排布好位置的型号，引用其脸型模板并
   `transform` 缩放/平移到真实尺寸和坐标，纯代码拼接，无需渲染引擎依赖。
4. **材质/花色**不单独建模板——同一脸型模板换填充色/花纹，或直接用标注文字体现材质名称。
5. **与"公司入驻规格录入会话"（FR-2）的联动**：录入某型号规格时，系统需额外确定它属于哪个
   脸型模板。RTA 行业型号命名通常自带这个信息（如 B12=12寸地柜单门、B15D=抽屉柜、
   W2430=30高吊柜、SB36=水槽柜），可先尝试规则匹配，匹配不到再通过对话询问用户确认。

## 4. 端到端场景走查

### 场景 A：通用设计讨论（总控助手）
客户描述大致需求（面积、布局、风格、预算），总控助手用通用知识追问关键信息，可建议
"发给几家公司看看谁能做"。

### 场景 B：向特定公司提问细节
`@公司名` 精确提问，公司 Agent 基于自己规格库确定性回答（能/不能，及替代方案）。

### 场景 C：上传户型图 → 生成初步平面设计
1. 客户上传户型图片（暂不支持 CAD 源文件；如果只有 CAD 图纸，引导客户截图后按图片处理）。
2. 系统用图像理解/OCR 估算房间轮廓与关键尺寸，精度到 1/4 英寸即可，但**完整性优先于精度**——
   拿不准的地方通过对话核对，或要求客户手动补充关键数字，不允许静默漏项。
3. 系统按客户指定/已 @ 的公司规格库，**全自动**生成一版初步方案（3.3 节的布局算法+模板拼接），
   客户不提供拖拽编辑器，只能通过对话提修改意见，系统据此重新生成受影响部分。
4. 产出四张图：正视图、俯视图-地柜层、俯视图-顶柜层、侧视图。

### 场景 D：报价确认与发送
1. 客户在对话中确认设计和报价单。
2. 若客户同时向多家公司询价，系统提供**价格对比**（表格形式的横向比较，不做图形/视图对比）。
3. 客户对某一家最终确认后，系统把该公司的报价发送到其登记的报价邮箱：
   - **HTML 邮件**，三视图拼图以 **CID 内嵌**方式显示在正文中，价格明细以 HTML `<table>`
     直接嵌入正文；同时把拼图作为普通附件兜底；必须同时提供 multipart/alternative 的纯文本
     版本（无 HTML 客户端兜底 + 降低被判定可疑邮件的概率）。
   - PDF 版正式报价单留白件列为后续迭代项（见第 9 节 MVP-3），不阻塞当前范围。
4. 发送前必须经过客户显式确认（见 FR-8 发送闸门），不可自动发送。

## 5. 功能需求（FR）

### FR-1　对话与 Agent 路由
- 单一对话框内多轮对话，维持通用上下文（需求摘要、已上传户型图、已选公司等）。
- `@公司名` 语法解析路由到对应公司 Agent，支持一句话内 @ 多家公司分别应答，`@` 时应有公司名联想。
- 公司 Agent 的知识边界限制在"自己的产品规格 + 客户当前项目上下文"。

### FR-2　公司入驻规格录入会话
- 每家公司独立的后台会话入口，可上传文件（产品手册/价格表/规格书，PDF/图片/Excel）。
- 系统持续追问，引导整理出结构化字段：柜体类型×尺寸矩阵、脸型模板归属（见 3.3 第 5 点）、
  花色/材质选项、五金选项、定价规则。
- 产出人类可读+结构化两种形式的"产品规格文档"，公司方可编辑修改，**确认后才发布**——未确认
  草稿不影响线上公司 Agent 的回答。
- MVP 阶段只挑 2-3 家公司完整走通此流程，不追求覆盖率。

### FR-3　户型图上传与解析
- 图像理解/OCR 估算房间轮廓与关键尺寸；精度 1/4 英寸颗粒度即可；不确定时对话核对或要求客户
  手动补充；不支持 CAD 源文件解析（引导截图代替）；解析结果必须覆盖所有相关区域，不允许漏项。

### FR-4　平面设计自动生成
- 全自动生成初步方案（布局算法 + 3.3 节模板拼接），仅使用目标公司规格库中真实存在的型号。
- 客户通过对话提修改意见触发局部重新生成，不提供可视化拖拽编辑器（MVP 阶段）。

### FR-5　三视图渲染（见 3.3 节，已定稿）
- 正视图、俯视图-地柜层、俯视图-顶柜层、侧视图，共四张图，基于脸型模板库参数化拼接生成。

### FR-6　报价单生成与多公司价格对比
- 结构化报价单：型号、数量、规格（尺寸/材质/花色）、单价、小计、总价、备注。
- 客户向多家公司询价时，提供价格层面的横向对比表（不做视图/图形对比）。

### FR-7　报价发送
- 发送内容：三视图拼图 + 价格明细表格，通过 HTML 邮件发送（CID 内嵌图片 + HTML 表格 + 纯
  文本兜底版本 + 图片附件兜底），详见场景 D。
- 发送目标为公司登记的报价邮箱。

### FR-8　发送闸门与数据隔离（硬性要求）
- **发送闸门**：客户必须在对话中显式确认设计+报价单，系统不得自动发送；沿用第一版 `email.ts`
  的"未配置发信凭据则 dry-run + 显式 confirm 才真正发送"两道闸门，及 CASL 合规注意事项
  （发件人身份透明、一次性真实询价性质）。
- **公司间数据隔离（程序层面硬校验，不只靠 prompt 约束）**：生成的设计/报价单**只能引用该公司
  规格库中真实存在的型号 id**；引用不存在的型号 id 时代码层面直接拒绝，不允许该报价继续生成
  或发送。

```
      widthOptions[], heightOptions[], depthOptions[],

  ]
  finishes: [{ name, priceModifier? }]

  pricingRule
  status: draft | published        # 新增：未发布草稿不对客户端生效

  category: singleDoor|doubleDoor|drawers|doorDrawerCombo|corner|sinkBase|openShelf|...

Conversation
  id, customerId, messages[]
  designRequirements
  perCompanyThreads: [{ companyId, messages[] }]

FloorPlan
  id, conversationId, sourceFile, parsedGeometry

DesignLayout (属于某个 FloorPlan + 某个 CabinetCompany)
  id, floorPlanId, companyId
  placedModules: [{ productSpecModuleId, position, dimensions }]  # moduleId 必须真实存在于该公司 ProductSpec
  views: { front, topBase, topWall, side }   # SVG 渲染产物
  status: draft | confirmed

Quote (属于某个 DesignLayout)
  id, designLayoutId, companyId
  lineItems: [{ moduleRef, qty, unitPrice, subtotal }]   # moduleRef 必须真实存在，硬校验（FR-8）

  status: draft | confirmed | sent | failed

QuoteComparison                    # 新增：多公司价格对比
  id, conversationId
  quotes: [{ companyId, quoteId, total }]
```

## 7. 非功能性需求

- **数据隔离**：见 FR-8，程序层面硬校验，不只靠 system prompt。
- **可追溯**：报价单发送前的每一版设计/报价都应可追溯。
- **可扩展**：新公司入驻 = 走一遍"公司入驻规格录入会话"即可上线，不需要改代码。
- **合规**：发送环节延续 CASL 合规注意事项。

## 8. MVP 分期建议（v0.2 更新）

- **MVP-1**：公司入驻规格录入会话（2-3 家跑通）+ 客户端多 Agent 对话（总控 + @公司路由）+
  报价单生成与确认发送闸门（先不含三视图，报价基于客户对话中直接描述的柜体清单）。
- **MVP-2**：户型图上传解析 + 自动排布算法 + 脸型模板库（3.3 节）+ 三视图渲染 + 多公司价格
  对比 + HTML 邮件发送（内嵌图+表格）。
- **MVP-3**：PDF 正式报价单留白件、体验打磨、（如需要）更复杂排布约束。

## 10. 已关闭的问题（v0.1 中的 7 项，供追溯）

1. 产品规格数据来源 → 公司入驻规格录入会话（FR-2）
2. 户型图尺寸获取 → 图像理解/OCR + 对话核对，1/4 英寸精度，不支持 CAD（FR-3）
3. 三视图渲染保真度 → 脸型模板库参数化拼接（3.3 节）
4. 排布自动化程度 → 全自动生成，仅对话式修改（FR-4）
5. 多公司对比 → 只做价格对比，不做图形对比（FR-6）
6. 报价单发送格式 → HTML 内嵌（图片 CID + HTML 表格）+ 纯文本兜底 + 图片附件兜底（FR-7）
7. 公司间数据隔离保障 → 程序层面硬校验型号 id（FR-8）

## 11. 新开放问题

1. **~15-25 个脸型模板由谁绘制？** 这些是示意性的"外框+分割线"图形，不需要专业插画师，可以
   用代码直接参数化生成（矩形+线条），或找人一次性手绘 SVG 定稿。倾向选哪种？
2. **PDF 正式报价单留白件放 MVP-3，是否认可这个优先级？**（场景 D 第 3 点已按此假设写）
3. **价格对比表的触发时机**：客户是要等所有意向公司都各自确认完设计后才看到对比表，还是可以
   随时拉出"当前几家草稿价格"做实时对比？
4. **FloorPlan 解析失败/置信度低的兜底交互**：目前只说"对话核对或要求手动补充"，具体触发
   阈值和交互形式（比如系统主动逐项追问 vs 客户自己发现不对再反馈）还需要细化。
